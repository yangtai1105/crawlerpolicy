# Web Intelligence Rearchitecture Design

Date: 2026-08-29

## Summary

Rebuild crawlerpolicy.com as a Web Content & Agentic Web intelligence product. The new system keeps the existing fetchers and Git-as-DB operating model, but replaces the three-pillar editorial model with an evidence-first pipeline, nine canonical intelligence tracks, persistent trend state, truthful health reporting, and a weekly synthesis generated by this repository's own automation.

The existing events remain available as a Legacy Archive. They are not reclassified or used to seed the new trend system. The ChatGPT scheduled task is a reference for scope and output quality only; this project will not connect to or depend on it.

## Product Goal

The site should answer four questions quickly:

1. What materially changed in the Web content and agentic Web ecosystem?
2. Why does the combination of those changes matter?
3. Which long-running trends accelerated, reversed, stalled, or remained stable?
4. How complete and trustworthy was the underlying monitoring run?

The primary audience is a product, policy, or strategy reader who needs a concise operating picture rather than a reverse-chronological news feed.

## Scope

### Included

- Clean-break source and event taxonomy.
- Nine canonical intelligence tracks aligned with the existing Web Ecosystem Weekly task.
- Multi-track classification for material events.
- Source tiering and source roles.
- Evidence preservation before LLM analysis.
- Pipeline health that distinguishes attempted, fetched, analyzed, and published states.
- A repository-native weekly intelligence generator.
- Persistent trend state and week-over-week deltas.
- New homepage, intelligence, front, event, source-health, and archive experiences.
- Existing event pages retained through a Legacy Archive.

### Excluded

- Connecting to or importing output from the ChatGPT scheduled task.
- Re-fetching or reclassifying historical events.
- Automated email subscriptions or notification delivery.
- A database or server-side application backend.
- User accounts, personalization, or collaborative editing.

## Information Model

### Canonical tracks

Every new material event has one `primary_track` and zero or more additional `tracks` selected from:

| Key | Display name | Scope |
|---|---|---|
| `policy-regulation` | Policy & Regulation | Government policy, regulator action, statutory rules, competition remedies |
| `litigation-legal` | Litigation & Legal Precedent | Complaints, rulings, settlements, legal tests and precedent |
| `search-discovery` | Search & AI Discovery | Search indexing, AI answers, citation, visibility, referral and publisher controls |
| `crawler-controls` | Crawlers & Content Controls | Crawler documentation, robots directives, verification, blocking and enforcement |
| `agentic-web` | Agentic Web & Agent Traffic | User-delegated agents, traffic identity, detection, blocking and human delegation |
| `licensing-monetization` | Licensing & Monetization | Direct and collective licensing, payment rails, marketplaces and commercial terms |
| `standards-protocols` | Standards & Protocols | IETF, RFC, W3C, Web Bot Auth, CoMP and interoperable protocol work |
| `asset-rights` | Content Rights & Asset-Level Controls | TDMRep, IPTC, PLUS, RSL, C2PA and image/video/audio rights |
| `measurement-economics` | Measurement & Ecosystem Economics | Crawl volume, citation, referral, traffic exchange, revenue and market measurements |

Tracks are multi-valued because a single development can affect policy, technical control, and economics simultaneously.

### Public fronts

The website groups the nine tracks into five browsable fronts without discarding the exact track labels:

1. **Access & Discovery** — `crawler-controls`, `search-discovery`
2. **Agents & Identity** — `agentic-web`, `standards-protocols`
3. **Rights & Markets** — `licensing-monetization`, `asset-rights`
4. **Governance & Law** — `policy-regulation`, `litigation-legal`
5. **Measurement & Economics** — `measurement-economics`

Fronts are presentation groupings. Tracks are the canonical data model and filtering primitive.

### Sources

Sources no longer belong to a single editorial pillar. `sources.yaml` retains fetch configuration and gains:

```yaml
- slug: google-search-central
  type: rss_feed
  url: https://example.test/feed.xml
  display_name: Google Search Central
  default_tracks:
    - search-discovery
    - crawler-controls
  tier: primary
  role: platform-docs
  required_for_coverage: true
```

Allowed source tiers:

- `primary` — official documentation, standards bodies, regulators, courts and original filings.
- `measurement` — first-party datasets or transparent empirical research.
- `specialist` — domain reporting and analysis with strong sourcing.
- `commentary` — discovery and perspective; cannot independently support a top-level thesis.

The `role` field records how the source contributes, for example `platform-docs`, `standards`, `regulator`, `legal-primary`, `publisher`, `infrastructure`, `measurement`, or `reporting`.

### Evidence

Fetching and evidence preservation occur before relevance or analysis calls. Each newly observed diff or feed item receives an evidence record containing:

- Stable evidence ID.
- Source and source URL.
- Publication time when available.
- Detection time.
- Raw or normalized content pointer.
- Fetch result and hash/guid.
- Pipeline stage status.
- Analysis attempts and last error.

Existing snapshots and raw JSONL files remain valid storage mechanisms. The refactor adds a normalized evidence index so failed LLM calls can be replayed without re-fetching and without marking the evidence as fully processed.

### Material events

New event frontmatter uses the following shape:

```yaml
schema_version: 2
slug: google-adds-ai-search-publisher-control
title: Google adds a separate AI Search publisher control
source: google-search-central
source_tier: primary
primary_track: search-discovery
tracks:
  - search-discovery
  - crawler-controls
event_date: 2026-08-27T00:00:00Z
published_at: 2026-08-27T00:00:00Z
detected_at: 2026-08-27T08:00:00Z
source_url: https://example.test/item
change_kind: material
importance: 0.86
confidence: high
```

`event_date`, `published_at`, and `detected_at` remain separate. The site must never imply that an old baseline became a new event merely because it was detected recently.

The analysis output contains:

- Factual development.
- Why it matters.
- Track assignments.
- Affected actors.
- Supported trend evidence.
- Confidence and source-quality notes.

### Trends

`data/trends.json` stores 8–12 durable themes. Each trend has:

- Stable key and title.
- Current status: `accelerating`, `stable`, `emerging`, `reversing`, or `stalled`.
- Previous status.
- Current thesis.
- Evidence event IDs.
- Last material update.
- Week-over-week delta explanation.

Trend generation may propose changes, but it may only cite material events with primary or measurement support. Commentary can add context but cannot be the sole evidence for a status change.

### Weekly intelligence

`pipeline/weekly_intelligence.py` generates `data/intelligence/YYYY-Www.json` from:

- Material events in the completed seven-day window.
- The previous weekly intelligence issue.
- Current trend state.
- Source and pipeline health for the same window.

The issue schema includes:

- `executive_shifts`: 3–5 ecosystem shifts.
- `material_developments`: grouped by track, including explicit quiet tracks.
- `intelligence_read`: cross-event synthesis.
- `trend_deltas`: old status, new status, evidence and explanation.
- `actor_moves`: major actor direction changes.
- `watchlist`: questions to verify in future weeks.
- `source_ledger`: every source used, with tier and dates.
- `coverage`: successful and degraded source counts.

The generator is repository-native and runs after the final daily ingestion for the weekly window. It does not call or read the ChatGPT scheduled task.

## Pipeline Architecture

The daily pipeline becomes four explicit stages:

1. **Fetch** — retrieve source material and save snapshots/raw items.
2. **Evidence** — create or update replayable evidence records.
3. **Analyze** — classify relevance, materiality, tracks, actors and trend evidence.
4. **Publish** — write schema-v2 event documents and update derived aggregates.

State advances independently by stage. In particular:

- A successful fetch followed by an LLM failure remains `fetched`, not `complete`.
- The evidence stays queued for analysis replay.
- A source's fetch health is not conflated with its analysis health.
- A derived aggregate failure does not erase successfully written events.

### Health semantics

`data/health.json` becomes a truthful operational summary:

```json
{
  "status": "degraded",
  "last_attempted_at": "...",
  "last_fully_successful_at": "...",
  "coverage": {
    "configured": 45,
    "fetched": 42,
    "analyzed": 37,
    "failed": 8,
    "required_failed": 3
  },
  "stages": {},
  "per_source": {}
}
```

Status rules:

- `healthy`: no required source failed and at least 95% of configured sources completed.
- `degraded`: one or more optional sources failed, or completion is 70–94%.
- `critical`: a required source failed, completion is below 70%, or weekly intelligence could not be generated.

The GitHub Actions job must exit non-zero on `critical`. A degraded run may complete but must display a warning in both the workflow summary and website.

Secrets and provider availability receive an explicit preflight before source processing. A missing dependency marks only affected sources, but missing dependencies that disable a required coverage lane make the run critical.

## Website Architecture

### Primary navigation

- **Intelligence** — latest weekly issue and archive.
- **Developments** — verified schema-v2 event feed with track filters.
- **Fronts** — the five public front pages.
- **Sources** — coverage map, source tier and operational status.
- **Legacy Archive** — current pre-refactor events and old dispatches.
- **About** — methodology and model disclosure.

### Homepage

The homepage is an operating picture, not a source index. In order:

1. Weekly thesis and coverage window.
2. Health strip showing coverage truthfully.
3. Three to five executive shifts.
4. Five fronts with current thesis, latest evidence date and active track deltas.
5. Trend Tracker showing only status changes first, then stable themes.
6. Latest verified developments.
7. Persistent watchlist.

If no material event exists in a stated window, the page says so. It never fills a 30-day section with events outside that window.

### Weekly Intelligence

`/intelligence` shows the current issue. `/intelligence/YYYY-Www` provides stable archives. Each issue exposes source tier, event date, publication date, and direct primary links next to supported claims.

The existing `/reading` collection moves under Legacy Archive and remains accessible. It no longer occupies the primary weekly product position.

### Developments and events

The new feed supports exact track, front, actor, source tier, and date filtering. Event pages distinguish evidence from synthesis:

- Development.
- Why it matters.
- Trend impact.
- Sources and dates.
- Raw diff or evidence excerpt when available.

### Sources and health

The source page displays:

- Coverage lane and default tracks.
- Tier and role.
- Last fetch success.
- Last analysis success.
- Consecutive failures.
- Latest material event.

The footer shows `Last fully successful run`, not merely the last attempt.

### Legacy Archive

Existing event files and dispatch JSON remain intact and accessible. They are moved into legacy collections or explicitly marked `schema_version: 1`. They do not appear in new homepage counts, trend calculations, or current-window intelligence.

Existing event URLs should remain valid where practical. If route conflicts require a move, static redirects preserve those URLs.

## Visual Direction

The subject is Web governance and machine access, and the site's single job is to make a complex, shifting control plane legible. The visual system should feel like a precise protocol observatory rather than a generic news site or analytics dashboard.

The signature element is an **evidence rail**: a restrained vertical line connecting a weekly thesis to the dated primary evidence and trend delta supporting it. Everything else remains quiet and information-dense. Track labels encode meaning consistently; health warnings use explicit language rather than decorative status colors alone.

The final frontend design pass will define typography, color tokens, spacing, responsive behavior, keyboard focus and reduced-motion handling before implementation.

## Error Handling

- Failed fetches preserve the previous good snapshot and do not advance fetch completion.
- Failed analyses retain evidence in the replay queue.
- Missing primary evidence prevents publication of high-confidence legal, standards, or official-control claims.
- Aggregate generation failures preserve the last good aggregate with a visible stale timestamp.
- Weekly intelligence does not publish when its required coverage threshold is unmet; the site displays the last verified issue with a degradation notice.
- All model-generated synthesis is labeled; source data and raw diffs remain authoritative.

## Testing

### Python

- Source schema validation for tracks, tiers, roles and coverage requirements.
- Evidence state transitions and replay behavior.
- Multi-track analyzer output validation.
- Event date versus detection date serialization.
- Health threshold calculations and exit behavior.
- Trend delta rules and evidence-tier requirements.
- Weekly intelligence schema, quiet-track behavior and previous-week comparison.
- Legacy events excluded from new aggregates.

### Astro

- Content collection validation for schema-v2 and legacy events.
- Static build includes new routes and preserves legacy routes.
- Homepage windowing never displays out-of-window events.
- Health strip renders healthy, degraded and critical states.
- Filters and front mappings use canonical track keys.
- Mobile, keyboard focus and reduced-motion checks.

### End-to-end verification

- Run a fixture pipeline with one successful source, one fetch failure and one analysis failure.
- Confirm the successful event publishes, failed evidence remains replayable, and health becomes degraded or critical according to source requirements.
- Generate two fixture weeks and confirm a trend delta compares week N to week N-1.
- Build and inspect the static site at desktop and mobile widths.

## Rollout

1. Introduce canonical tracks, source metadata, schema-v2 events and health primitives behind tests.
2. Add evidence replay and replace three-pillar digest generation with weekly intelligence and trend state.
3. Add the new Astro collections and pages while retaining the current site as Legacy Archive.
4. Switch the homepage and navigation to the new product.
5. Add the expanded source set by coverage lane.
6. Enable critical/degraded workflow behavior after validating one manual run.

The initial launch may have a sparse new feed. That is intentional: the new product begins with verified post-refactor evidence rather than presenting old material as current intelligence.
